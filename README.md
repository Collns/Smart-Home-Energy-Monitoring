## 1. What this project is

Households see one electricity bill but have no idea **which appliance** is driving it. This project is an end-to-end IoT system that monitors the power use of six home appliances, spots abnormal behaviour, and shows live and historical usage on a dashboard, so people can find the worst devices and move loads off peak hours.

The simulator, broker, processor and Grafana run locally with Docker Compose; storage is in **Azure Data Explorer (ADX)** in the cloud. Seven layers in total:

```
 ┌──────────────────┐  publish (QoS 1)   ┌──────────────────────┐
 │ 1. Device layer  │ ─────────────────▶ │ 2–3. Mosquitto broker│
 │ 6 simulated plugs│   TLS :8883        │ auth + ACLs + persist│
 └──────────────────┘                    └──────────┬───────────┘
                                                    │ subscribe home/+/+/power
                                         ┌──────────▼───────────┐
                                         │ 4. Python processing │
                                         │ clean · aggregate ·  │──▶ home/alerts (QoS 2)
                                         │ Isolation Forest     │
                                         └──────────┬───────────┘
                                                    │ write
                                                    │ streaming ingestion (HTTPS)
 ┌──────────────────┐   KQL query        ┌──────────▼───────────┐
 │ 6. Grafana       │ ◀───────────────── │ 5. Azure Data        │
 │ live + history   │  (ADX plugin)      │    Explorer (cloud)  │
 └──────────────────┘                    │ raw 30d · rollups 1y │
                                         └──────────────────────┘
          7. Security & reliability applies across every layer
```

### Appliances (in scope)

| Appliance        | Room          | Behaviour to simulate                         |
|------------------|---------------|-----------------------------------------------|
| Refrigerator     | kitchen       | Compressor cycles on/off all day              |
| Microwave        | kitchen       | Short, high bursts around meal times          |
| Washing machine  | laundry       | Intermittent cycles (fill, wash, spin)        |
| Water heater     | utility       | Heating spikes after hot-water use            |
| Air conditioner  | living_room   | Peaks in the afternoon                        |
| Television       | living_room   | Steady load in the evening                    |

**Out of scope:** remote control of appliances, mobile apps, utility billing API integration.

### Success criteria (from the proposal)

- Device → dashboard latency **under 2 s**
- **Zero** lost readings at QoS 1 during a broker restart
- Anomaly model catches **≥ 90 %** of injected faults with a low false-alarm rate
- Alerts fire **within 10 s** of a threshold breach
- **Zero** lost readings when the connection to Azure drops and comes back (local buffer)

> The < 2 s latency target now includes the internet round trip to Azure and depends on ADX streaming ingestion. If it can't be met, revise the target in the report.

## 4. Shared contract (agree on this first)

All three parts can be built in parallel **as long as everyone sticks to these formats**. Changes go through a pull request that all three approve.

**Reading topic:** `home/{room}/{appliance}/power` · QoS 1

```json
{
  "device_id": "plug-fridge-01",
  "room": "kitchen",
  "appliance": "refrigerator",
  "ts": "2026-11-04T18:30:05Z",
  "seq": 1042,
  "power_w": 142.6,
  "voltage_v": 120.3,
  "current_a": 1.19
}
```

**Status topic (Last Will):** `home/{room}/{appliance}/status` · retained · payload `online` / `offline`

**Alert topic:** `home/alerts` · QoS 2

```json
{
  "ts": "2026-11-04T18:31:00Z",
  "appliance": "air_conditioner",
  "type": "threshold",          // or "anomaly"
  "severity": "warning",
  "value": 2150.0,
  "message": "AC above 2000 W for 30 min"
}
```

**Azure Data Explorer** · database `SmartHomeEnergy`

| Table / view            | Kind              | Retention | Columns                                                          |
|-------------------------|-------------------|-----------|------------------------------------------------------------------|
| `PowerRaw`              | table             | 30 days   | `ts:datetime, device_id, room, appliance, seq:long, power_w:real, voltage_v:real, current_a:real` |
| `Power1m`               | materialized view | 365 days  | `bin(ts,1m), room, appliance, avg_w`                             |
| `EnergyHourly`          | materialized view | 365 days  | `bin(ts,1h), room, appliance, kwh`                               |
| `Alerts`                | table             | 365 days  | `ts:datetime, appliance, type, severity, value:real, message`    |

Streaming ingestion is enabled on `PowerRaw` and `Alerts` so data shows up within seconds (the default queued ingestion can take minutes).

**Azure access (least privilege)**

| Identity                 | ADX role          | Used by     |
|--------------------------|-------------------|-------------|
| `sp-processor`           | Database Ingestor | processor   |
| `sp-grafana`             | Database Viewer   | Grafana     |

Client IDs and secrets live in `.env` only.

**MQTT users & ACLs**

| User        | Can write                  | Can read            |
|-------------|----------------------------|---------------------|
| `plug-*`    | its own `.../power`, `.../status` | –            |
| `processor` | `home/alerts`              | `home/+/+/power`, `home/+/+/status` |
| `monitor`   | –                          | `home/#` (debugging) |

## 5. Team split

The proposal lists four roles (A–D). With three people, A and B are merged because the simulator and the broker are tightly linked.

### Part 1 – Devices, Broker & Security · *Mashal Niazi* (roles A + B)

- Python simulator: one thread per appliance, a reading every 5 s, realistic profiles (fridge cycling, AC afternoon peak, washer cycles)
- Inject noise, dropped packets, malformed JSON and **labelled faults** (e.g. fridge running nonstop) so Part 2 can measure detection rate
- Last Will messages, persistent sessions, reconnect with exponential backoff
- Mosquitto config: persistence to disk, username/password, per-client ACLs
- TLS on port 8883 with a self-signed CA (`scripts/gen_certs.sh`)
- QoS 1 for readings, QoS 2 for alerts
- Azure security: Entra ID app registrations for the processor and Grafana, least-privilege ADX roles, secret handling in `.env`
- **Owns test:** broker restart → zero lost readings at QoS 1

### Part 2 – Processing, ML & Alerts · *Collins Ehirim* (role C)

- Subscribe to `home/+/+/power`; drop malformed or out-of-range readings, fill short gaps
- Write clean readings to ADX with streaming ingestion (`azure-kusto-ingest`)
- Local buffer: if Azure is unreachable, keep readings on disk and resend when it's back
- Daily totals and any aggregates not covered by ADX materialized views
- Threshold alerts (e.g. AC > 2000 W for 30 min) → publish to `home/alerts` and write to the `Alerts` table
- Train an Isolation Forest per appliance on the first week of simulated data (can be generated quickly by running the simulator in fast-forward mode)
- ML anomaly alerts through the same alert path
- **Owns tests:** ≥ 90 % fault detection with low false alarms; alerts within 10 s; Azure outage → zero lost readings

### Part 3 – Storage, Dashboard & Integration · *Issaq Momand* (role D)

- `docker-compose.yml` for the local services, `.env` handling
- Create the ADX cluster (free tier if it fits) and database; keep all setup as KQL scripts in `adx/`
- Tables, JSON ingestion mappings, retention policies, streaming ingestion, materialized views
- Grafana provisioned automatically with the ADX data source; all panels written in KQL: live gauges per appliance, stacked daily/weekly energy, peak-hour heatmap, Ontario time-of-use cost estimate, alert panel
- Keep an eye on Azure cost and free-tier limits
- GitHub setup: branch protection, PR template, README upkeep
- **Owns test:** end-to-end latency under 2 s (compare `ts` in the payload with the write/display time)

### Shared

- Final report, demo video and presentation – each person writes their own layer's section
- Code review: every PR needs one approval from another member

## 7. Getting started

```bash
git clone https://github.com/<your-org>/smart-home-energy.git
cd smart-home-energy
cp .env.example .env              # MQTT passwords + ADX cluster URI, tenant ID, client IDs/secrets
./scripts/gen_certs.sh            # creates CA + broker certs for TLS
docker compose up -d --build
```

**One-time Azure setup** (done once by Part 3, then shared):

1. Create an ADX cluster (free tier if limits allow) and a database `SmartHomeEnergy`.
2. Run `adx/01_tables.kql`, `02_policies.kql`, `03_views.kql` in the ADX web UI.
3. Create the `sp-processor` and `sp-grafana` app registrations and grant their ADX roles.
4. Put the cluster URI, tenant ID and client credentials in each member's `.env`.

| Service   | URL / port                  |
|-----------|-----------------------------|
| Mosquitto | `localhost:8883` (TLS)      |
| ADX       | your cluster URI (Azure)    |
| Grafana   | http://localhost:3000       |

Watch the raw stream while debugging:

```bash
mosquitto_sub -h localhost -p 8883 --cafile mosquitto/certs/ca.crt \
  -u monitor -P <password> -t 'home/#' -v
```

## 8. Change from the proposal

The proposal named InfluxDB 2.x for storage. The team switched to **Azure Data Explorer** for cloud-hosted, scalable time-series storage. Only storage changed: Flux queries became KQL, InfluxDB buckets became ADX tables and materialized views, and Azure access (Entra ID, least-privilege roles) was added to the security layer. *Confirm this change with the instructor.*
